## 流程 1：登录认证（双重哈希 + JWT）

**参与文件**：前端（crypto-js）→ [AuthController](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/controller/AuthController.java) → [UserService](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/service/UserService.java) → Sa-Token

```
① 前端：GET /api/auth/salt/{username} 拿到该用户的盐 salt
② 前端：clientHash = SHA256(salt + 输入密码)
③ 前端：POST /api/auth/login { username, password: clientHash }
④ 后端：查用户 → 查 enabled → BCrypt.checkpw(clientHash, 库中BCrypt值)
⑤ 通过：StpUtil.login(userId) → 生成 JWT → 存入 Redis（登录态）
⑥ 返回：token + userId + 三个权限布尔
⑦ 前端：存 token，之后每个请求带 Authorization 头
⑧ 后端：SaInterceptor 每个请求验 token → getLoginIdAsLong() 取用户
```

**三张可以口头画出来的图**：

```
创建用户时：  明文 → [前端]SHA256(盐+明文) → [后端]BCrypt → 入库
登录校验时：  输入明文 → [前端]SHA256(盐+明文) → [后端]BCrypt.checkpw → 通过/拒绝
会话流转：    login → JWT(token) ←→ Redis(会话) → 请求带token → 拦截器验证
```

**为什么 JWT 还要 Redis？** JWT 本身无状态可自验，但无法主动"踢人"。
Sa-Token 把登录态同时存 Redis，服务端 `logout()` 可立即失效——**"无状态 token + 有状态会话存储"的折中设计**（support主动注销）。

## 流程 2：客服 SSE 流式聊天（一条消息的一生）

**参与文件**：[ChatController](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/controller/ChatController.java) → [ChatService](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/service/ChatService.java) → [CustomerServiceGraph](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/graph/CustomerServiceGraph.java) → [ChatClientFactory](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/config/ChatClientFactory.java)

```
客户         前端Vue          ChatController      ChatService        大模型API
 │ 发消息       │                   │                  │                 │
 │───────────▶│ GET /chat/stream   │                  │                 │
 │            │──────────────────▶│ 解析IP           │                 │
 │            │                   │───────────────▶ │ 0 校验参数      │
 │            │                   │                  │ 1 建GraphContext│
 │            │                   │                  │ 2 流程图execute │
 │            │                   │                  │ 3 Redis读历史   │
 │            │                   │                  │ 4 拼本轮问题    │
 │            │                   │                  │ 5 选模型客户端  │
 │            │                   │                  │ 6 拼system提示  │
 │            │                   │                  │ 7 prompt().stream()▶
 │   ◀ ─ ─ ─ ─ ─ ─ ─ ─ SSE 数据流（token一个接一个）─ ─ ─ ─ ─ ─ ─ ─ ─ │
 │  打字机效果  │                   │                  │    doOnNext收集 │
 │            │                   │                  │ 8 doOnComplete  │
 │            │                   │                  │  ├─写Redis(窗口) │
 │            │                   │                  │  └─@Async存MySQL │
```

**为什么是 SSE 而不是 WebSocket？**

| | SSE | WebSocket |
|---|---|---|
| 方向 | 单向：服务器 → 客户端 | 双向 |
| 协议 | 纯 HTTP（text/event-stream） | 升级协议 |
| 实现 | 一个注解 + Flux | 需要专门 handler |
| 适用 | 问答流式输出（本项目） | 即时通讯/游戏 |

客服场景只要"模型回答流式推给用户"，SSE 足够且更轻——**技术选型意识**是面试加分点。

**Flux 链式调用的三个回调**（响应式经典套路）：

```java
chatClient.prompt()...stream().content()
    .doOnNext(fullResponse::append)      // 每来一个 token 就拼进 StringBuilder
    .doOnComplete(() -> {...})           // 流正常结束：存记忆+落库
    .doOnError(e -> log.error(...));     // 异常：只记日志，不打断用户
```

## 流程 3：AI 记忆（Redis + MySQL 双层）

```
                        ┌─────────────────────────────┐
 用户提问/回答 ──▶ 写 ──▶│ Redis List（admin:chat:memory:ID）│
                        │  • 最多 40 条（20 对）      │
                        │  • 超限从头部成对淘汰       │
                        │  • TTL 24 小时             │
                        └─────────────────────────────┘
                                 │ 异步落库
                                 ▼
                        ┌─────────────────────────────┐
                        │ MySQL chat_message（永久）   │
                        │  • history 接口读这里       │
                        └─────────────────────────────┘
```

- **读路径**：每次提问前 `loadHistory` 从 Redis 读最近记忆 → 拼进 messages → 模型获得上下文；
- **写路径**：回答完 `saveToRedis`（滑动窗口）+ `@Async` 写 MySQL；
- **查路径**：`GET /chat/history` 直接查 MySQL（全量历史）。

**为什么两级？**（高频面试题）
1. Redis 内存快、适合频繁读写，但会过期、不宜无限膨胀 → 存"最近上下文"；
2. MySQL 持久可靠、可全量查询 → 存"永久档案"。
3. 直连数据库做上下文会有延迟和压力，每次聊天都查库不划算。
> 一句话：**Redis 是草稿纸，MySQL 是档案室。**

**扩展点（可以主动讲）**：当前 Redis 记忆没有"历史融入的条数裁剪"（全量 20 对都进 prompt），
优化方向是加**记忆摘要**（把早期历史压缩成摘要再拼上下文），控制 token 消耗。

## 流程 4：RAG 知识库（上传 → 向量化 → 检索）

**参与文件**：[KnowledgeController](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/controller/KnowledgeController.java) → [KnowledgeService](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/service/KnowledgeService.java) → VectorStore（Milvus）

### 4.1 写入（离线）

```
管理员上传 PDF/Word/TXT
   │
   ├─▶ MinIO 存原文件（yyyy/MM/dd/uuid.ext）
   ├─▶ MySQL 存元数据（status=pending）
   ├─▶ 同步返回分块预览（按空行分段）
   └─▶ @Async 异步向量化：
        pending → processing
        分词分块 TokenTextSplitter(500/50)
        每块 Embedding → 1536 维向量
        写入 Milvus（集合 ai_knowledge_base，度量 COSINE）
        processing → completed（或 failed + errorMsg）
```

### 4.2 检索（在线问答时）

```
用户提问 "退货政策是什么？"
   → Embedding 成向量 q
   → Milvus similaritySearch：找与 q 最相似的 top-5 片段
   → 片段文本拼进 system 提示词："根据以下检索到的信息回答……"
   → 大模型基于片段生成回答（可溯源）
```

**RAG 的三个作用**（面试背这个）：
1. **让模型"知道"私有数据**（大模型没训练过你公司的资料）；
2. **降低幻觉**（回答被检索片段约束）；
3. **知识可更新**（上传新文档即可，不用重新训练模型）。

> ⚠️ 关键事实重申：`spring.ai.vectorstore.milvus.enabled` 默认 `false`（用 dummy 空实现）。
> **完整 RAG 需要：开启该开关 + Milvus 服务可达 + 有效的 Embedding API Key。**
> 当前 `CustomerServiceGraph.retrieveKnowledge` 也只是占位。理解这一点，
> 你就能在面试中区分"设计实现"与"当前状态"，并主动讲改进路线（接上 KnowledgeService.retrieve）。

## 流程 5：多模型动态切换（ChatClientFactory 主战场）

```
后台管理：新增/编辑/启停模型（ai_model 表）
                │ ModelService.save + evictCache
                ▼
聊天请求带 modelName
                │ ChatService.buildChatClient(modelName)
                ▼
查库 findByModelNameAndEnabledTrue
                │ 未找到/未启用 → 默认模型（sort_order 最大）
                ▼
ChatClientFactory.getChatClient(model)
                │
    ┌───────────┴────────────┐
    │ baseUrl 为空？          │
    ▼ yes                    ▼ no
DashScope 通道            OpenAI 兼容通道
(通义千问，只覆盖模型名)   OpenAiApi(baseUrl, apiKey) → OpenAiChatModel
    │                        （DeepSeek / Ollama / 任何 /v1/chat/completions）
    └───────────┬────────────┘
                ▼
     clientCache（ConcurrentHashMap 按键缓存）
                ▼
     chatClient.prompt()...stream()  —— 上层完全无感
```

**为什么上层无感？** 因为所有客户端最终都是 `ChatClient` 接口——**策略模式 + 工厂模式 + 缓存**三合一：

- 工厂模式：按配置"生产"不同客户端；
- 策略模式：ChatClient 接口统一调用方式，运行时切换实现；
- 缓存兜底：`computeIfAbsent` 避免重复构建 + `evictCache` 保证配置变更一致性。

> 面试被打断问"你用到了什么设计模式"，**这就是标准答案**。
