## 11.1 简历上的项目描述（可直接改写的模板）

### 项目名：AI 智能客服系统（企业级 AI 应用）

> **一句话**
> 基于 Spring Boot 3 + Spring AI Alibaba 的企业级 AI 客服平台，支持多模型动态切换、RAG 知识库、SSE 流式对话、AI 记忆与可视化流程编排。

> **职责描述（后端，按 STAR 组织）**
> - **多模型动态切换**：设计 ChatClientFactory，模型配置存 MySQL，聊天时按 baseUrl 区分 DashScope 与 OpenAI 兼容协议动态构建 ChatClient，配 ConcurrentHashMap 缓存 + 配置变更缓存失效，实现后台热切换无需重启；
> - **AI 记忆**：采用 Redis List 滑动窗口（最近 20 对消息、TTL 24h）作短期上下文，MySQL 作长期归档，流式响应结束后 @Async 异步落库，兼顾性能与持久性；
> - **流式对话**：基于 WebFlux `Flux<String>` + SSE 实现 token 级流式输出，比轮询体验更实时、比 WebSocket 更轻量；
> - **认证与权限**：Sa-Token + JWT 实现无状态认证（Redis 存储会话支持主动注销），前端 SHA256(盐+密码)、后端 BCrypt 双重哈希防拖库；三模块布尔权限实现极简 RBAC；
> - **RAG 知识库**：文档上传 MinIO，TokenTextSplitter 分块 + Embedding 向量化写入 Milvus，问答时 CosinE 相似度检索 Top-K 片段注入提示词；
> - **流程编排**：基于 Spring AI Alibaba Graph 定义"意图识别→知识检索/业务执行→回复生成"节点图，前端可视化展示，后端执行复用同一套命名常量；
> - **工程化**：全局异常处理器 + 统一 Result 响应 + ResultCode 枚举消灭魔法数字；Mapper 方法名生成 SQL；Docker 多阶段构建 + Compose 七服务编排（含健康检查依赖、数据卷、固定子网）。

> **面试官最爱追问的三行，你要有把握**：多模型工厂的实现、双重哈希的因果、Redis 记忆的窗口策略。

## 11.2 高频面试题与参考答案要点

### 基础篇（Java / Spring）

**Q1：Spring Boot 自动配置原理？**
> 核心是 `@EnableAutoConfiguration` → `META-INF/spring.factories`(新版 `AutoConfiguration.imports`) 注册的自动配置类 + `@ConditionalOnXxx` 条件装配。本项目实例：VectorStoreConfig 里 `@ConditionalOnProperty(milvus.enabled)` 决定注册真 Milvus 还是 dummy 空实现。

**Q2：@Autowired 和构造器注入的区别？为什么项目用构造器注入？**
> 项目里统一 `@RequiredArgsConstructor`（Lombok 生成 final 字段构造器）——构造器注入保证依赖不可变、便于测试、避免字段注入的"隐式依赖"；`@EnableAsync`/`@Transactional` 等也更好配合。

**Q3：Spring 事务在哪用的？**
> ModelService/UserService 的写操作用 `@Transactional`（如 update 里"改库 + evictCache"要保证原子性）。注意：ChatService 的 `persistMessages` 是 @Async——自调用或异步线程里 @Transactional 有失效场景，这是可以展开聊的点。

**Q4：@Async 怎么实现的？失效场景？**
> 依赖启动类 `@EnableAsync`；本质 Spring AOP 代理 + 线程池执行。失效典型：**同类内自调用**（this.method 不走代理）、方法非 public、忘加 @EnableAsync。本项目里 @Async 定义在 Service 的 public 方法、由 Controller 调用——路径安全。

**Q5：JPA 和 MyBatis 的选择？**
> 项目用 JPA：实体驱动、方法名派生查询，适合本项目"表少、查询模式简单"的场景；MyBatis 适合 SQL 复杂多变的报表型系统。

### AI 应用篇（本项目特色，拉开差距的部分）

**Q6：什么是 RAG？为什么需要？**
> Retrieval-Augmented Generation：检索增强生成。大模型不知道私有数据/知识有时效，且可能幻觉。方案：文档分块 → Embedding 向量化进 Milvus → 提问向量相似度检索 top-k → 注入提示词再生成。三价值：私有知识、降低幻觉、知识热更新。

**Q7：Embedding 是什么？为什么分块？**
> Embedding 把文本映射成高维向量（本配置 1536 维），语义相近的文本向量距离近。分块原因：模型上下文有限 + 检索粒度需要（整篇文档进向量，命中率低、噪声大）。重叠（overlap 50）防止句子被切开丢语义。

**Q8：SSE 和 WebSocket 选型？**
> 客服问答单向流式推送，SSE 基于 HTTP 更轻、天然支持断线重连（EventSource）；WebSocket 双工但维护成本高。项目用 WebFlux `Flux<String>` 直接返回流。

**Q9：token 级流式输出的链路？**
> 后端 `chatClient.prompt().stream().content()` 返回 `Flux<String>`，每个下游 token 为一个元素；`doOnNext` 拼接全文，`doOnComplete` 存档；前端 EventSource 收到数据流逐字渲染（打字机效果）。

**Q10：AI 记忆为什么分层？滑动窗口细节？**
> Redis List 存最近上下文（快、自动过期，读历史每轮都要用），MySQL 永久归档（历史页查询）。窗口参数：20 对=40 条，超限 leftPop 成对淘汰最旧，每次写入刷新 24h TTL。可展开：后续可加"记忆摘要"控 token。

**Q11：多模型动态切换怎么做的？用了什么模式？**
> ChatClientFactory：模型配置存 MySQL（provider/baseUrl/apiKey）→ 按 baseUrl 空/非空走 DashScope 或 OpenAiApi 动态构建 → ConcurrentHashMap 缓存（computeIfAbsent）→ 配置变更 ModelService 调 evictCache。模式：工厂 + 策略 + 缓存一致性。启动时 @PostConstruct 取 sort_order 最大启用模型作默认。

**Q12：双重哈希设计？**
> 前端 SHA256(盐+密码) 防传输中泄露明文；后端 BCrypt 防拖库反推（自带随机盐+慢哈希）。校验：后端直接 `BCrypt.checkpw(clientHash, dbValue)`。

**Q13：Sa-Token 为什么选它？JWT + Redis 矛盾吗？**
> 比 Spring Security 轻；JWT 无状态可扩展，但无法服务端强踢人——所以会话再存 Redis，支持 logout 即时失效。拦截器规则分层：公开路由 match stop，管理路由 check 权限，兜底 /** 需登录。

**Q14：并发场景考虑过吗？**
> 可答：`volatile defaultChatClient`（多线程可见默认模型切换）；`ConcurrentHashMap` 缓存（线程安全 + computeIfAbsent 原子）；`@Async` 落库用独立线程池避免阻塞 SSE 线程；HikariCP 连接池参数调优。**不要吹"高并发百万 QPS"**，坦诚项目定位是中小企业客服。

### 诚实篇（应届生杀手锏）

**Q15：项目里你觉得做得不好的地方？如果重来/迭代会做什么？**
> 这是加分题，照实答（源码现状）：
> 1) RAG 检索目前是简化占位（Milvus 默认关闭、Graph 的 retrieveKnowledge 空实现）——下一步接入 KnowledgeService.retrieve + Embedding 接通，形成完整闭环；
> 2) 意图识别是关键词规则——演进为 LLM Function Calling 分类 + 接入 StateGraph 状态机；
> 3) 部分接口直接裸传 Entity（Model/User 的 CRUD）——统一收编为 DTO + MapStruct 映射；
> 4) 后端健康检查依赖 /actuator/health 但未引入 actuator 依赖——补依赖或换探活端点；
> 5) 客服记忆全量 20 对进 prompt——加摘要压缩控制 token；
> 6) chat_message 会无限增长——按月分表/归档。

## 11.3 术语表（小白扫盲版）

| 术语 | 大白话 | 项目位置 |
|---|---|---|
| **SSE**（Server-Sent Events） | 服务器用一条 HTTP 连接持续单向推数据，浏览器用 EventSource 收 | /chat/stream |
| **Flux** | WebFlux 的响应式流：0..N 个元素随时间依次发出 | 所有流式接口返回值 |
| **WebFlux** | Spring 响应式栈（Netty），非阻塞 | 与 MVC 共存 |
| **RAG** | 检索增强生成：先查资料再让模型作答 | KnowledgeService |
| **Embedding** | 把文字变成"语义坐标"（向量），近义=近距离 | 向量化用 text-embedding-v3 |
| **向量数据库** | 专门存向量、算相似度的库（本项目 Milvus） | MilvusVectorStore |
| **相似度检索** | 拿问题向量去库里找最像的几段话 | similaritySearch |
| **Top-K** | 检索返回最相似的 K 条（K=5） | app.knowledge.top-k |
| **滑动窗口** | 只保留最近 N 条，旧的自动淘汰 | max-messages: 20 |
| **TTL** | 数据存活时间，到期自动过期 | ttl-hours: 24 |
| **JWT** | 签过名的"身份身份证"，可自验证防篡改 | sa-token-jwt |
| **BCrypt** | 慢哈希密码算法，自带盐，抗暴力破解 | UserService |
| **盐（salt）** | 拼在密码前的随机串，让同密码产生不同哈希 | 每用户 UUID |
| **RBAC** | 基于角色的权限控制；"极简"=三布尔替代角色表 | perm_* 字段 |
| **魔法数字/字符串** | 散落代码里无名字的常数——维护灾难 | 项目用枚举/常量消灭 |
| **DTO** | 接口专用数据信封 | dto 包 |
| **ORM** | 对象关系映射：Java 对象 ↔ 数据库行 | JPA/Hibernate |
| **BOM** | 物料清单：批量统一控制依赖版本 | spring-ai-bom |
| **注解处理器** | 编译期生成代码的插件（Lombok/MapStruct） | maven-compiler-plugin |
| **@PostConstruct** | Bean 初始化后执行一次的方法 | initDefaultClient |
| **@Async** | 方法异步执行（依赖 @EnableAsync） | persistMessages/vectorizeAsync |
| **dummy 实现** | 空壳实现，让依赖存在但啥也不干（保证能启动） | dummyVectorStore |
| **CORS** | 跨域资源共享；预检(OPTIONS)后放行 | WebConfig |
| **Interceptor vs Filter** | Filter 更早（Servlet 层），Interceptor 在 MVC 层 | CORS 用 Filter |
| **多阶段构建** | 构建用一个镜像、运行用最小镜像 | Dockerfile |
| **healthcheck** | 容器健康探测，配合 depends_on 决定启动顺序 | docker-compose |
