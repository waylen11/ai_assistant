## 1. 多模型动态切换

### 一句话原理（背）
> "模型的配置信息存在 MySQL 里，聊天时按模型名查出来，动态构建调用大模型的客户端，所以后台换模型不用重启服务。"

### 必背 3 细节
1. **路由规则**：配置里 baseUrl 为空 → 走阿里云 DashScope 通道（通义千问）；baseUrl 不为空 → 按 OpenAI 兼容协议构建客户端（DeepSeek 等）。
2. **本地缓存**：构建好的客户端放进缓存（一个 Map），下次同名模型直接用，不用重复构建；后台改了配置就把这条缓存删掉（缓存失效），下次重新构建。
3. **为什么不用重启**：因为配置在数据库不在配置文件里，改完删缓存立即生效。

### 追问应对
- **Q：OpenAI 兼容协议是什么？**
  > "很多模型厂商都按照 OpenAI 的接口格式提供服务，都是同一个 /v1/chat/completions 的路径，只要换 baseUrl 和 apiKey，就能用同一套调用代码，接入新模型很方便。"
- **Q：为什么缓存要失效？不删会怎样？**
  > "后台改了 apiKey 或 baseUrl，缓存里的旧客户端还拿着旧配置，请求就会用错配置报错。所以更新、删除、启停模型时，主动把对应缓存清掉。"
- **Q：ChatClient 是什么？**
  > "是 Spring AI 提供的统一调用大模型的接口，屏蔽了不同厂商 API 的差异，换模型上层业务代码不用改。"

## 2. 流式对话输出

### 一句话原理（背）
> "接口基于 WebFlux 的 Flux 响应流，用 SSE 协议把大模型生成的内容一个 token 一个 token 推给前端，前端打字机式渲染，不用等整段回答生成完。"

### 必背 3 细节
1. **返回类型**：`Flux<String>` —— 0 到 N 个字符串随时间依次发出，大模型每吐一段就是一个元素。
2. **SSE**：Content-Type 是 `text/event-stream`，基于普通 HTTP，服务器单向持续推送，前端用 EventSource 接收。
3. **选型理由**：客服问答只需要"服务器→浏览器"单向推送，SSE 比 WebSocket 更轻、实现更简单，所以选 SSE。

### 追问应对
- **Q：和普通接口有什么区别？**
  > "普通接口是请求后等全部数据生成完，一次性返回完整 JSON；SSE 是连接保持着，服务器边生成边推，用户几乎立刻就能看到内容在逐字出现。"
- **Q：Flux 是什么？**
  > "WebFlux 响应式编程里的流，表示 0 到 N 个元素按时间顺序发出，特别适合这种持续产生数据的场景。"
- **Q：如果中途断线怎么办？**
  > "SSE 前端 EventSource 自带断线重连；我们的对话和记忆都落了库，刷新页面历史还在。"（答到这个程度够了）

## 3. AI 记忆分层存储

### 一句话原理（背）
> "对话记忆存两层：Redis 用 List 做滑动窗口，保存最近 20 轮对话作为短期上下文，24 小时过期；回答结束后再异步写入 MySQL 做永久归档。"

### 必背 3 细节
1. **滑动窗口**：Redis List 每轮对话从尾部追加"问题+回答"两条，最多保留 20 轮（40 条），超了就从头部弹出最旧的。
2. **TTL 24 小时**：每次写入都刷新过期时间，一天没聊自动清空。
3. **异步落库**：写 MySQL 用 @Async 异步执行，不阻塞用户收到完整回复。

### 追问应对
- **Q：为什么分两层？只用 MySQL 行不行？**
  > "每次对话前都要读历史拼上下文，Redis 是内存操作快；MySQL 慢但永久，适合存档和查历史记录。一个当草稿纸，一个当档案室。"
- **Q：为什么要限制 20 轮，不是越多越好吗？**
  > "大模型的上下文窗口有长度限制，而且按 token 计费，历史全塞进去又贵又可能超限。保留最近 20 轮，兼顾效果和成本。"
- **Q：异步落库用什么实现的？**
  > "Spring 的 @Async 注解，方法提交到线程池执行。注意要在启动类加 @EnableAsync 才生效。"

## 4. 认证与权限控制

### 一句话原理（背）
> "登录用 Sa-Token + JWT；密码是双重哈希——前端先 SHA256(盐值+密码) 再传输，后端收到后再用 BCrypt 加密存库；权限用用户表三个布尔字段控制模型、知识库、用户三个管理模块。"

### 必背 3 细节
1. **登录流程**：前端先请求该用户的盐值 → 本地算 SHA256(盐+密码) → 传给后端 → 后端用 BCrypt 校验 → 通过后签发 JWT token，之后每个请求带上 token。
2. **双重哈希防什么**：
   - 前端哈希 → 防**传输泄露**（就算被抓包，拿到的也是哈希值不是明文密码）；
   - 后端 BCrypt → 防**拖库反推**（BCrypt 自带随机盐 + 故意算得慢，彩虹表和暴力破解几乎无效）。
3. **三模块权限**：用户表 3 个布尔字段（permModel / permKnowledge / permUser），拦截器按请求路径检查对应字段，false 就返回 403。

### 追问应对
- **Q：BCrypt 和 MD5 有什么区别？**
  > "MD5 快，反而适合暴力破解；BCrypt 故意设计得慢，而且每次加密自动生成随机盐，同样的密码每次存出来的值都不一样，数据库泄露也很难反推。"
- **Q：JWT 是什么？**
  > "一个签了名的字符串，里面带用户 ID 等信息，后端验签就能确认身份，不需要查库；特点是服务端无状态，容易扩展。"
- **Q：拦截器怎么实现权限检查的？**
  > "注册一个拦截器拦截所有请求，公开接口（登录、客服聊天）直接放行；管理接口先校验登录，再根据路径检查用户对应的权限字段。"

## 5. RAG 知识库问答

### 一句话原理（背）
> "文档上传后存到 MinIO 对象存储，后台异步把文本分块、用 Embedding 模型向量化，写进 Milvus 向量库；用户提问时，把问题也向量化，按相似度检索出最相关的 Top-K 个片段，拼进 Prompt 让大模型基于这些资料回答。"

### 必背 4 细节（流程背成一句话链）
> **上传 → 存 MinIO → 分块 → 向量化 → 存 Milvus → 提问检索 Top-K → 拼 Prompt 回答**

1. **为什么需要 RAG**：大模型没见过我们公司的资料，直接问会瞎编（幻觉）；RAG 让它"开卷考试"。
2. **向量是什么**（通俗版）："把一段文字换算成一组数字坐标，意思相近的文字坐标距离近。"
3. **Top-K**：检索返回相似度最高的 K 条（K 一般取 5）。
4. **分块**：把长文档切成小块（如 500 字一块，块之间重叠 50 字），重叠是为了防止句子被切断丢失语义。

### 追问应对
- **Q：为什么不把整个文档直接塞给模型？**
  > "一是上下文窗口装不下大文档，二是整篇塞进去噪声大、token 费用高。检索出最相关的几段再给模型，又准又省。"
- **Q：相似度检索怎么做的？**
  > "问题和文档块都变成向量后，用余弦相似度算距离，Milvus 里找出离问题向量最近的 K 个块。"
- **Q：向量化的过程是同步的吗？**
  > "不是，文档比较大时分块和向量化耗时，是异步执行的，上传接口先返回，向量化在后台跑完更新状态。"

## 6. 工程规范建设

### 一句话原理（背）
> "所有接口统一返回 Result 对象，格式是 code、message、data；全局异常处理器把所有异常兜底翻译成统一格式；状态码和常量都用枚举和常量类定义，消灭魔法数字。"

### 必背 3 细节
1. **统一响应**：前端只需要判断 `code == 200`，一套逻辑处理所有接口；错误码（401 未登录 / 403 无权限 / 500 系统错误）统一在枚举里。
2. **全局异常处理器**：`@RestControllerAdvice` + `@ExceptionHandler`，任何层抛的异常都在这里收口，返回友好提示而不是把堆栈甩给用户；参数校验失败（@Valid）也会在这里拼出具体哪个字段错了。
3. **消灭魔法数字**：直接写 200、401 别人看不懂意图；用 `ResultCode.OK` 这种枚举，看得懂、改一处全局生效、写错编译期就报错。

### 追问应对
- **Q：全局异常处理器原理？**
  > "Spring MVC 的 @RestControllerAdvice 会拦截所有 Controller 抛出的异常，按 @ExceptionHandler 匹配的异常类型分别处理，最后包装成统一的 Result 返回。"
