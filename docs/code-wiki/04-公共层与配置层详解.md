## 4.1 common 公共层

### 4.1.1 Result<T> —— 统一响应信封

源码：[Result.java](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/common/Result.java)

所有接口的返回都是这个形状：

```json
{ "code": 200, "message": "success", "data": {...} }
```

| 静态工厂方法 | 用途 | 产生的 code |
|---|---|---|
| `Result.ok(data)` | 成功返回数据 | 200 |
| `Result.ok()` | 成功无数据 | 200 |
| `Result.fail(message)` | 业务失败（自定义文案） | 500 |
| `Result.fail(resultCode)` | 失败（用标准状态码） | 对应枚举 |
| `Result.unauthorized()` | 未登录 | 401 |
| `Result.forbidden()` | 无权限 | 403 |

**为什么前端要统一格式？**（面试必背）
1. 前端只需写一套 `if (res.code === 200)` 的判断逻辑；
2. 出错路径（401 跳登录、403 提示无权限）可统一拦截处理；
3. 分页、错误详情等扩展字段可以无痛塞进 `data`。

> 细节：构造器私有（`private Result(){}`）+ 静态工厂方法，表示"只能通过工厂造信封，不允许随手 new"——
> 这是简单工厂思想的体现。还有个 `@Deprecated` 的 `fail(Integer, String)`，注释写明"禁止魔法数字"，
> 说明项目刻意引导大家只用枚举——这种**工程规范意识**面试时提一嘴很加分。

### 4.1.2 ResultCode —— 状态码枚举

源码：[ResultCode.java](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/common/ResultCode.java)

```java
OK(200, "success"),
BAD_REQUEST(400, "请求参数错误"),
UNAUTHORIZED(401, "请先登录"),
FORBIDDEN(403, "没有操作权限"),
NOT_FOUND(404, "请求的资源不存在"),
NOT_ACCEPTABLE(406, "不支持的响应格式"),
INTERNAL_ERROR(500, "系统内部错误，请稍后重试");
```

**为什么用枚举而不用数字？** 数字是"魔法数字"，写 `200` 别人不知道你是"成功"还是碰巧；枚举自解释 + 编译期检查。

### 4.1.3 GlobalExceptionHandler —— 全局异常兜底

源码：[GlobalExceptionHandler.java](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/common/GlobalExceptionHandler.java)

`@RestControllerAdvice` = 给所有 Controller 套一个"错误售后服务站"，
任何层抛出的异常最终都在这里被翻译成统一 `Result`：

| 捕获的异常 | 返回 |
|---|---|
| `NoResourceFoundException`（静态资源不存在） | 404 |
| `HttpMediaTypeNotAcceptableException`（Accept 头不支持） | 406 |
| `NotLoginException`（Sa-Token：没登录） | 401 |
| `NotPermissionException`（Sa-Token：没权限） | 403 |
| `MethodArgumentNotValidException` / `BindException`（@Valid 校验失败） | 400 + 拼接具体字段错误 |
| `IllegalArgumentException`（业务主动抛的"参数不对"） | 400 + 具体信息 |
| `Exception`（最后的网） | 500，隐藏细节（日志已记录） |

**面试亮点**：参数校验失败时用 stream 把每个字段的错误拼接成一句话返回，
比如"用户名不能为空, 密码不能为空"——前端能直接展示，而不是甩个干巴巴的 500。

## 4.2 config 配置层

### 4.2.1 ChatClientFactory —— ★ 多模型热切换的发动机

源码：[ChatClientFactory.java](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/config/ChatClientFactory.java)

**它解决的问题**：传统做法把模型配置写死在 yml，换模型要改配置+重启。
这个工厂让模型信息存进 MySQL（`ai_model` 表），聊天时按名字动态造客户端，**后台增删改模型即时生效**。

**四个成员变量**：

| 成员 | 类型 | 作用 |
|---|---|---|
| `dashScopeClientBuilder` | `ChatClient.Builder` | Spring AI Alibaba 自动装配的通义千问构建器 |
| `defaultChatClient` | `ChatClient`（volatile） | 默认客户端，启动时从数据库加载 |
| `defaultModelName` | `String`（volatile） | 当前默认模型名（日志追踪用） |
| `clientCache` | `ConcurrentHashMap<String, ChatClient>` | 按模型名缓存客户端，避免每次重建 |

> `volatile` + `ConcurrentHashMap` 的组合：多线程能看到最新的默认客户端、缓存操作线程安全——并发意识。

**核心方法逐个拆**：

```java
@PostConstruct
public void initDefaultClient()
```
- 启动完成后执行：`findFirstByEnabledTrueOrderBySortOrderDesc()` 取 **sort_order 最大的启用模型**当默认；
- 数据库为空/连不上 → 保留 DashScope 裸客户端兜底 + 打 warn 日志，**不让启动失败**。

```java
public ChatClient getChatClient(AiModel model)   // 路由规则（最核心）
```
1. `model == null` → 直接用默认客户端；
2. `baseUrl` 为空 → 视为通义千问：用 `dashScopeClientBuilder` 覆盖 model 名构建（`buildDashScopeClient`）；
3. `baseUrl` 非空 → 视为 OpenAI 兼容协议（DeepSeek/Ollama…）：`buildOpenAiCompatibleClient` 手动构造。

```java
private ChatClient buildOpenAiCompatibleClient(baseUrl, apiKey, modelName)
```
- `normalizeBaseUrl`：去末尾 `/` 和 `/v1`（OpenAiApi 内部会自己拼 `/v1/chat/completions`）；
- `OpenAiApi.builder()...build()` → `OpenAiChatModel.builder()...build()` → `ChatClient.builder(chatModel).build()`；
- 温度固定 0.7（defaultOptions）。

```java
public void refreshDefaultClient()   // 重新从数据库刷默认
public void evictCache(modelName)    // 移除单模型缓存（配置更新后调用）
public void clearCache()             // 清空全部缓存
```

**为什么要有缓存 + 失效？** 造一个 ChatClient 要建连接、设参数，有成本；
但模型 apiKey/baseUrl 被改后旧客户端还拿着旧配置会出错，所以 ModelService 在 update/delete/toggle 时调 `evictCache`。

> **闭眼能画的流程图**：
> `streamChat → buildChatClient(modelName) → 查库拿 AiModel → ChatClientFactory.getChatClient(model) → baseUrl 空? 通义客户端 : OpenAI兼容客户端 → ChatClient.prompt().stream()`
> 这一整条就是"多模型动态切换"的完整实现，面试讲 3 分钟没问题。

### 4.2.2 SaTokenConfig —— 鉴权闸门

源码：[SaTokenConfig.java](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/config/SaTokenConfig.java)

注册一个 `SaInterceptor`，拦截 `/**`，规则如下：

| 路径 | 规则 |
|---|---|
| OPTIONS 请求 | 一律放行（CORS 预检） |
| `/chat/**` | 公开（客服免登录） |
| `/auth/**` | 公开（登录/盐值本身要能访问） |
| `/models/enabled` | 公开（前端下拉框要拿模型列表） |
| `/admin/models/**` | 登录 + `permModel` 权限 |
| `/admin/knowledge/**` | 登录 + `permKnowledge` 权限 |
| `/admin/users/**` | 登录 + `permUser` 权限 |
| `/assistant/**` | 仅登录 |
| 其余 `/**` | 仅登录 |

`checkPermission(PermissionField)` 的实现套路：
1. `StpUtil.checkLogin()`（未登录抛 `NotLoginException`）；
2. `StpUtil.getLoginIdAsLong()` 拿到 userId → 查库拿用户；
3. `switch(permissionField)` 取出对应布尔权限 → 为 false 抛 `NotPermissionException`。

> 注意：这里的"权限"不是 Sa-Token 的 `rbac` 模块字符串角色，而是**读 sys_user 表里三个布尔字段**的极简 RBAC——
> 设计上更直白，面试时能讲清楚（见 09 章 sys_user 表）。

### 4.2.3 WebConfig —— CORS 为何用 Filter 而非 Interceptor？

源码：[WebConfig.java](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/config/WebConfig.java)

类注释写得很清楚，这是**项目里一个真实踩过的坑**：

> Sa-Token 拦截器会在 Spring MVC 处理 OPTIONS 预检请求之前返回 401/403，
> 浏览器预检失败。CorsFilter 是 Servlet Filter，**优先级高于 Interceptor**，
> 能在 Sa-Token 介入之前完成 CORS 握手。

**执行顺序**：Filter 链（CorsFilter）→ DispatcherServlet → Interceptor（SaInterceptor）→ Controller。
所以把 CORS 放 Filter 层，OPTIONS 直接 200 返回，根本不进 Sa-Token。

配置内容：允许来源来自 [CorsProperties](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/config/CorsProperties.java)（读 `app.cors.*` 配置）+ 三个 localhost 兜底；`allowCredentials(true)`（允许带 Authorization 头）；预检缓存 1 小时。

`@ConfigurationProperties(prefix = "app.cors")` 是这个类的第二个知识点：
把 yml 里 `app.cors.allowed-origins` 列表自动绑定进 Java 对象的 `List<String>` 字段。

### 4.2.4 RedisConfig —— 自定义序列化

源码：[RedisConfig.java](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/config/RedisConfig.java)

默认 `RedisTemplate` 用 JDK 序列化（存进去是乱码、占用大、跨语言不友好）。
这里改成：**Key 用 String 序列化，Value 用 Jackson JSON 序列化**——

```java
template.setKeySerializer(stringSerializer);
template.setValueSerializer(jsonSerializer);
```

并且 `activateDefaultTyping(...NON_FINAL)`：JSON 里带上类信息（`@class`），
反序列化时才能还原成正确的 Java 对象类型。

> 不过本项目 ChatService 实际用的是 `StringRedisTemplate`（key/value 都是字符串），
> 它内部已经用 String 序列化器，RedisConfig 主要服务 Sa-Token 的会话存储（sa-token-redis-jackson 有自己的序列化）。
> 面试时说"自定义 Redis 序列化避免 JDK 乱码"即可。

### 4.2.5 MinioConfig —— 造一个 MinIO 客户端 Bean

源码：[MinioConfig.java](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/config/MinioConfig.java)

```java
@Bean
public MinioClient minioClient() {
    return MinioClient.builder()
            .endpoint(endpoint)
            .credentials(accessKey, secretKey)
            .build();
}
```

用 `@Value("${minio.endpoint}")` 读配置 → 注册成 Bean → KnowledgeService 直接注入使用。
**这是"第三方 SDK 对象交给 Spring 管理"的标准姿势**：把"怎么造对象"放 config，
业务代码只管注入使用，符合依赖倒置。

### 4.2.6 VectorStoreConfig —— ★ 条件装配（@ConditionalOnProperty）

源码：[VectorStoreConfig.java](../../ai-customer-service-backend/src/main/java/com/huangyuanwei/aics/config/VectorStoreConfig.java)

两个互斥的 Bean 根据配置开关二选一：

```java
@Bean @Primary
@ConditionalOnProperty(name = "spring.ai.vectorstore.milvus.enabled", havingValue = "true")
public VectorStore milvusVectorStore(...)   // 真 Milvus 客户端

@Bean
@ConditionalOnProperty(name = "spring.ai.vectorstore.milvus.enabled", havingValue = "false")
public VectorStore dummyVectorStore()       // 空实现（不连 Milvus 也能启动）
```

**为什么要 dummy？** KnowledgeService 注入了 `VectorStore` 接口。
如果 Milvus 没开而又不提供实现类，Spring 启动直接报"找不到 Bean"。
给一个空实现兜底，**项目在没装 Milvus 的机器上也能跑起来**（只是检索返回空）。

> ⚠️ **必须知道的事实**：`application.yml` 里 `milvus.enabled` 默认是 `false`！
> 也就是说**默认配置下 RAG 检索是不生效的**（用的是 dummy 空实现）。
> 想要完整跑通 RAG，需要把 `spring.ai.vectorstore.milvus.enabled` 改成 `true` 并保证 Milvus 可达。
> 面试被问到"你来部署/改进会做什么"，这就是现成的答案素材。

另外该类还注册了 `defaultChatClient` Bean（`@Primary @Qualifier("defaultChatClient")`），
充当 ChatClientFactory 注入的"裸 DashScope 客户端"起点。
