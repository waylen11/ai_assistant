## 9.1 ER 关系总览

```
sys_user (用户)
   │ 1
   │
   ├─────< chat_session (会话，user_id 外键，级联删除)
   │          │ 1
   │          │ (session_id 字符串关联，无硬外键)
   │          └─────< chat_message (消息，memory_id 记录归属)
   │
   ├─────< knowledge_base (上传人 upload_user_id，软关联)
   │
   └─────< workflow_graph (创建人 created_by，软关联)

ai_model (模型配置) —— 独立配置表，被消息记录引用 model_name（软关联）
```

**设计特点**：只有 `chat_session.user_id` 一个**硬外键**（`ON DELETE CASCADE`），
其他关系都是"存字符串/ID 的软关联"——互联网项目为**查询性能与解耦**常这样做，
面试时能解释为什么（硬外键拖慢大表写入、约束跨服务扩展）。

## 9.2 逐表详解

### ① ai_model —— 模型配置表

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键自增 |
| model_type | VARCHAR(64) | qwen / deepseek / gpt |
| model_name | VARCHAR(128) | **UNIQUE**，如 qwen-max |
| provider | VARCHAR(64) | 厂商 |
| description | TEXT | 简介 |
| api_key | VARCHAR(512) | 密钥 |
| base_url | VARCHAR(512) | 空=通义；非空=OpenAI 兼容端点 |
| multimodal | TINYINT(1) | 多模态 |
| icon_url | VARCHAR(512) | 图标 |
| enabled | TINYINT(1) | 启用 |
| sort_order | INT | 排序权重 |
| created_at / updated_at | DATETIME | 时间戳 |

索引：`uk_model_name`（唯一）、`idx_enabled`、`idx_provider`。
初始化数据：qwen-max / qwen-plus / qwen-vl-max / qwen-turbo / deepseek-chat 五条（`ON DUPLICATE KEY UPDATE` 幂等）。

### ② sys_user —— 系统用户表

| 字段 | 说明 |
|---|---|
| username | UNIQUE 登录名 |
| password | **BCrypt(SHA256(salt+明文))**，VARCHAR(256) |
| salt | 每用户随机盐 |
| nickname/avatar_url/gender/department/position/email/phone | 资料 |
| **perm_model / perm_knowledge / perm_user** | 三权限布尔（极简 RBAC） |
| enabled | 启停 |
| last_login_at | 最近登录 |

**极简 RBAC 的取舍**：不建 role/role_permission 表，直接三个布尔字段。
优点：够用、直观、查询零 join；缺点：加第四种权限要加列。
> 面试主动讲："系统权限维度少且固定（模型/知识库/用户），用标志位比引入完整 RBAC 表更简单可靠；若权限维度增多会演进为角色表。"

初始化管理员：`admin / admin123`。
推导链（schema.sql 注释里有）：`salt='aics2026'` → `SHA256('aics2026admin123')=1c8337e...` → `BCrypt(...)` 入库。

### ③ chat_session —— 会话表（助理模式）

| 字段 | 说明 |
|---|---|
| session_id | **UNIQUE** UUID，同时是 Redis memoryId |
| user_id | 外键 → sys_user（**CASCADE 删除**） |
| title | 默认"新会话"，首问后截前 20 字 |
| model_name | 会话使用模型 |
| message_count | 计数（每次+2） |
| last_message_at | 列表排序键（`idx_last_message_at`） |

### ④ chat_message —— 消息表

| 字段 | 说明 |
|---|---|
| memory_id | VARCHAR(128)：**客服=IP / 助理=sessionId**（一字段两义） |
| session_id | 助理模式关联会话 |
| role | user / assistant / system |
| content | LONGTEXT |
| model_name | 当时模型 |
| tokens | 预留（未启用） |
| source | service / assistant |
| created_at | 时间轴 |

索引：`idx_memory_id`、`idx_session_id`、`idx_created_at`、`idx_source_role`（组合）。

> 分表思考题（加分）：消息表按时间无限增长，生产环境可考虑按月分表或归档冷数据——这类"对未来容量有意识"的表达很受面试官欢迎。

### ⑤ knowledge_base —— 知识库表

| 字段 | 说明 |
|---|---|
| file_name / file_size / file_type | 原文件 |
| minio_bucket / minio_path | MinIO 位置 |
| chunk_count / chunk_size / chunk_overlap | 分块参数 |
| **vector_status** | 状态机 pending/processing/completed/failed（`idx_vector_status` 供异步监控） |
| vector_collection | Milvus 集合 |
| error_msg | 失败原因 |
| upload_user_id | 上传人 |

### ⑥ workflow_graph —— 流程图表

| 字段 | 说明 |
|---|---|
| graph_name / description | 名称 |
| graph_json | LONGTEXT：节点+边 JSON |
| version | 每次更新 +1 |
| enabled / graph_type | 开关与类型（customer_service） |
| created_by | 创建人 |

初始化一条"默认客服流程"（意图→知识/业务→回复四节点 JSON）。

## 9.3 建表脚本的可学之处

1. **幂等**：`CREATE TABLE IF NOT EXISTS` + `INSERT ... ON DUPLICATE KEY UPDATE`，脚本可重复执行；
2. **注释文化**：每张表、每字段都有 COMMENT，中文说明（这是工程素养）；
3. **字符集**：全程 `utf8mb4`（emoji 安全）；
4. **索引设计**：每个 WHERE/ORDER BY 高频字段都有索引（memory_id、vector_status、enabled…）；
5. **时间字段**：`DEFAULT CURRENT_TIMESTAMP` + `ON UPDATE CURRENT_TIMESTAMP`，与 JPA 的 `@CreationTimestamp/@UpdateTimestamp` 双保险。

## 9.4 JPA 与脚本的配合方式

`application.yml`：`ddl-auto: validate` —— **Hibernate 只校验不建表**（生产推荐），
表结构完全由 schema.sql 主导；本地首次跑可临时改 `create`。
> 面试问"你们建表谁负责？"答：schema.sql 是唯一真源，JPA validate 启动时校验实体与表结构一致性，不一致直接启动失败——"DDL 让出控制权"也是种规范。
